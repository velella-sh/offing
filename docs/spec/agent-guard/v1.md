# Agent Guard protocol v1

A caller sends a check before adding a dependency or writing a file. The
guard returns a lifecycle decision supported by the data it consulted. A
caller can implement the protocol independently of Offing and use it with
any transport.

## Request

Send a JSON object with `schemaVersion` set to `offing.agent-guard.request.v1`
and exactly one of `purl` or `snippet`. The
[request JSON Schema](https://velella.sh/offing/schemas/agent-guard-request.v1.schema.json)
describes the wire format.

| Field | Type | Meaning |
| --- | --- | --- |
| `purl` | string | A [Package URL](https://github.com/package-url/purl-spec). Include the intended version in the PURL when known. |
| `snippet` | object | The intended file with `path` and `content`. The path is repository-relative, uses forward slashes, and has no `..` segment. Content is the exact UTF-8 text to check. |
| `language` | optional string | A language hint for a snippet, such as `javascript` or `python`. The path still supplies file and manifest context. Omit the hint for dependency checks. |
| `context` | optional object | Per-request policy. Its optional `failOn` is one of `info`, `low`, `medium`, `high`, `critical`, or `none`. The default is `high`. |

The guard treats the supplied text as data. A request authorizes a check of
its explicit subject. A snippet path is at most 256 characters, and its
content is at most 1,000,000 bytes encoded as UTF-8. The language hint
has at most 64 characters. The request grants no permission to execute code, perform an
install or edit, or inspect other files.

```json
{
  "schemaVersion": "offing.agent-guard.request.v1",
  "purl": "pkg:npm/request@2.88.2",
  "context": { "failOn": "high" }
}
```

```json
{
  "schemaVersion": "offing.agent-guard.request.v1",
  "snippet": { "path": "src/client.js", "content": "export const endpoint = '/api';\n" },
  "language": "javascript"
}
```

## Response

Return a JSON object with `schemaVersion` set to
`offing.agent-guard.response.v1`, a `decision`, and a non-empty `reason`
that explains the result in terms of the subject and any applicable policy.
The [response JSON Schema](https://velella.sh/offing/schemas/agent-guard-response.v1.schema.json)
describes the wire format. A reason and replacement may be at most 350
characters each. An evidence URL may be at most 1,000 characters.

| Decision | Host behavior | When to return it |
| --- | --- | --- |
| `allow` | May proceed. | The check completed with no applicable finding and enough data to make that determination for the checked subject. |
| `warn` | May proceed after surfacing the reason. | A finding is below the configured threshold or blocking is disabled, or the guard lacks the version or lifecycle data needed to decide. |
| `block` | Must stop the proposed operation. | An applicable finding meets or exceeds the configured threshold. |

Severities increase in the same order as in the request table. When findings
have different severities, use the highest to determine the decision. For an
unversioned dependency, a rule applying to every version can still produce a
finding. If only some versions are affected, ask for the intended version
in the warning reason. For an allowed snippet, limit the reason to what the
check covered.

When known, include a `replacement` string naming the recommended alternative
and a `source` string containing an absolute HTTP or HTTPS URL for the
underlying evidence. If both are present, the source must support the reason,
and the replacement must address that same finding. Omit unavailable fields.
A missing rule or source supplies no evidence of safety. Invalid requests and
failed checks are errors reported by the transport. They do not carry an
`allow`, `warn`, or `block` decision.

```json
{
  "schemaVersion": "offing.agent-guard.response.v1",
  "decision": "block",
  "reason": "request is deprecated and meets the high severity threshold.",
  "replacement": "Native fetch or a maintained HTTP client",
  "source": "https://www.npmjs.com/package/request"
}
```

## Transports

Each transport sends the request and response objects defined above. A
completed check has the same response for the same request and lifecycle
data regardless of transport. Clients select a dialect by its
`schemaVersion`.

### Standard input and output

A command reads one UTF-8 JSON request from standard input through EOF.
It writes one UTF-8 JSON response followed by a newline to standard
output and exits zero for each valid decision, including `block`. The
caller enforces the decision. When a request or check fails, the command
exits nonzero, reports the error on standard error, and leaves standard
output empty. Offing's protocol command is `offing guard --protocol`.

### Model Context Protocol

Call `agent_guard` with the request object as the tool's `arguments`.
The tool returns the response object as `structuredContent`. If it also
returns text, it serializes the same response. A failed check uses the
tool error channel (`isError` with diagnostic content). The existing
`check_dependency` and `check_snippet` tools continue to return their
finding documents.

### Host hooks

A host adapter extracts the proposed dependency or snippet from its
hook event and sends a protocol request. For a supported pre-operation
event, it maps the resulting decision to that host's native hook
response. It leaves a permitted operation alone, surfaces the reason
for a warning, and denies a blocked operation through the host's
native mechanism. Post-operation hooks can report a finding within
the host's feedback channel because the operation has already run.
An event outside the hook's supported scope is handled as a host
event without sending a check request.

## Existing Offing entry points

Offing also exposes the full package and snippet findings through [`check_dependency` and `check_snippet`
in MCP](../../MCP.md#tools), and through [`offing check` and `offing
check-snippet`](../../CLI.md#check-snippet) in the CLI. Those checks return
their versioned findings. [Install guard](../../guard.md) already applies its
own severity gate before running the package manager.

## Conformance

Download [check.mjs](conformance/check.mjs) and [fixtures.json](conformance/fixtures.json)
into the same directory. With Node.js 22 or newer, run the checker against any
command that implements the standard input and output binding.

```sh
node check.mjs offing guard --protocol
```

The suite compares decisions and evidence, allowing each implementation to
write its own reason. It exits 1 if a fixture fails and prints
`acc-guard-protocol` on success. The fixtures use the supported and deprecated
subjects documented in the test data. Run them against an Offing release
with the matching bundled lifecycle data.

The [standalone example](example/guard.mjs) has a small local dataset for
those subjects and does not import Offing. Use it to see how to implement a
binding and run the suite in an empty directory.

```sh
node check.mjs node guard.mjs
```
