# Offing verification result v1

The [JSON Schema](https://velella.sh/offing/schemas/verify-result.v1.schema.json)
describes the standalone document, identified by
`schemaVersion: "offing.verify-result.v1"`.

| Field | Meaning |
| --- | --- |
| `before`, `after` | Each scan's `commit`, `offingVersion`, and `ebbDataVersion`. An unavailable value is `null`. A Git commit identifies the checked-out HEAD when the scan was taken. Files in the worktree may differ from that commit. |
| `resolved` | Findings reported only by the before scan, with their before values. |
| `remaining` | Findings with IDs in both scans, with their after values. |
| `introduced` | Findings reported only by the after scan, with their after values. |
| `counts` | The length of each corresponding finding list. |
| `verdict` | `passed` when no findings remain or were introduced and no command failed. Otherwise `failed`. |
| `commands` | Suggested commands from the findings, including purpose and execution evidence when available. |

Finding matching uses the exact `id` string. The three lists are disjoint, each
ID is unique, and the lists are ordered by ascending UTF-16 code units of the
ID. Each finding has `id`, `rule`, `title`, `severity`, `path`, and an optional
one-based `line`.

Command strings are unique and sorted by ascending UTF-16 code units. When
several findings suggest the same command, the first purpose in the
comparison order wins: resolved findings in before-scan order, then remaining
and introduced findings in after-scan order.

| Command status | `exitCode` | `logSha256` |
| --- | --- | --- |
| `not-run` | `null` | `null` |
| `skipped` | `null` | `null` |
| `passed` | `0` | Lowercase 64-digit SHA-256 of the recorded log bytes |
| `failed` | Positive integer | Lowercase 64-digit SHA-256 of the recorded log bytes |

Offing's receipt, fix, and MCP verification commands produce `not-run` for
suggested commands. The verdict covers lifecycle findings and supplied command
evidence. Run your project's checks before declaring a migration complete.

## CLI and MCP

`offing receipt . --before before.json --format verify-result` compares a
saved `offing.scan.v1` with a fresh scan. A legacy saved scan can lack
`identity` and `data`. Missing identity values stay `null`.

`offing fix . --branch --json` prints the same contract after applying and
committing deterministic fixes locally. When no fix is available, it
compares the scan to itself and writes no commit. Dry-run JSON still prints
the fix plan. The command exit code retains the existing CLI policy.

MCP `verify_migration` adds `verifyResult` next to its existing fields. Near the
answer size limit, `receipt_markdown` can point to an artifact while the
structured field still carries the complete document. If the structured field
itself cannot fit alongside the existing fields, the tool omits it whole,
returns `verifyResultUnavailable: "tool-size-limit"`, and keeps the Markdown
summary. Use the CLI with the saved before scan for the complete document.

## Pull request receipts

A Markdown receipt contains this block after its human-readable summary:

~~~markdown
<!-- offing-verify-result:v1 -->
```json
{ ...complete offing.verify-result.v1 document... }
```
~~~

Consumers look for the exact marker on its own line, followed immediately by
a JSON fence or the artifact line. The limit is 48 KiB (49,152 UTF-8 bytes)
for the fenced block including fences and the two line breaks. When it would
exceed that size, the marker is followed by this line instead:

```text
Artifact: `offing-verify-result.json`
```

Put the complete document in the producer's associated CI run as
`offing-verify-result.json`. A workflow or host that uploads artifacts can
include the run link after the block. Offing's local receipt command only
prints the reference, so a local caller can save the artifact with
`--format verify-result` and attach it separately.

## Conformance

Download [check.mjs](https://velella.sh/offing/spec/verify/conformance/check.mjs).
It runs with Node.js 22 or newer, without Offing or npm dependencies.

```bash
node check.mjs verification.json
node check.mjs verification.json before.json after.json
```

The second form independently rebuilds identities, finding lists and
suggested commands from two scans and compares them with the document. It
validates execution evidence for consistency, since scans do not contain
command logs or exit codes. Either form exits nonzero on invalid input.
