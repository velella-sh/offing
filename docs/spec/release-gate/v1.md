# Offing release gate v1

## Inputs

Supply one of the following inputs.

| Input | Evidence |
| --- | --- |
| Directory | Findings and unclassified references from an offline repository scan |
| Git ref | The same scan of the local committed tree, with working-copy changes and archive export filters excluded |
| SBOM | Component PURLs and versions from a CycloneDX, SPDX 2.3, or Syft JSON SBOM, resolved against local Ebb data |
| Signed [lifecycle attestation](../lifecycle-attestation/v1.md) | Lifecycle observations from the signature-verified statement |

For an attestation, verify the bundle against the artifact bytes, expected repository, expected signing workflow, and an independently obtained trust root. Validate the statement against the lifecycle attestation specification and re-evaluate its absolute dates. Use the dates in the authenticated statement. If verification fails, emit an input error. Offing delegates cryptographic verification to the GitHub CLI in offline mode and consumes the single statement that it verified.

A gate covers only the evidence available in its input. A repository scan describes the references its detectors recognize. An SBOM describes the supplied inventory. An attestation describes the components observed by its authenticated signer.

## Window and verdict

The release day is today's day in UTC unless another day is specified. The inclusive end of the support window is either the release day plus a non-negative whole number of days (30 by default) or an explicit UTC calendar date on or after the release day. The day count for an event is its UTC calendar day minus the release day. Zero means the event is on the release day. Negative counts are overdue. For example, a February 29 deadline is one day away on February 28, 2024.

Report a blocking reason when an applicable `end-of-support`, `end-of-life`, `scheduled-end-of-life`, or `removed` rule has a confirmed deadline on or before the end of the window. A deprecation alone does not establish a support deadline. Predictions are advisory and must never trigger a block. This implementation consumes published Ebb rules and verified attestation observations. Forecast predictions have no published input binding yet.

Treat an unclassified component, a component whose missing version prevents classification, or a known lifecycle event without a deadline as `no-data`. An empty SBOM or attestation is also a missing-evidence observation.

- `fail` produces a blocking reason.
- `warn` produces a warning and is the default.
- `ignore` omits the observation from the output.

Evaluate matching exceptions in the repository's lifecycle policy. For a local directory or Git ref, load its repository configuration. For SBOM and attestation input, load configuration relative to the invocation directory. A path or ecosystem scope uses the same matching rules as the scan policy. A matching exception covers the rule through its expiry date, inclusive. A matching expired exception takes precedence over any active match. It leaves the rule blocking and supplies its expiry and rationale. Exceptions apply to identified lifecycle rules.

The decision is `block` if any reason blocks, `warn` if at least one reason warns and none blocks, or `pass` in all other cases. An active exception is recorded as an `excepted` reason.

## Decision document and exit status

The [release gate JSON Schema](https://velella.sh/offing/schemas/release-gate.v1.schema.json) defines `offing.release-gate.v1`. Each decision has an input kind and label, a verdict, and a list of reasons. Deadlines include the rule ID, calculated days left, available locations, and evidence links. Rollback readiness uses the same document, with the requested `releaseRef` and one decision per named candidate tag in request order. Every rollback candidate is evaluated against the same window and the configuration at that candidate ref. The workflow event or date of a candidate tag does not select the release day.

| Exit | Meaning |
| --- | --- |
| 0 | Evaluation completed and all candidates pass or warn. |
| 1 | Evaluation completed and at least one input was blocked. |
| 2 | Invalid arguments, unavailable Git ref, or invalid configuration. |
| 3 | Requested lifecycle data could not be loaded. |
| 4 | Invalid date, SBOM, artifact, or attestation, including failed signature verification. |
| 5 | Unexpected processing error. |

JSON writes the decision document. SARIF 2.1.0 includes block and warning results and preserves the decision document at `runs[0].properties.offingReleaseGate`. A command that cannot complete evaluation reports the ordinary Offing error instead of a decision. The Action publishes its decision in the Job Summary.

## Conformance

Download `check.mjs` and `fixtures.json` from the [conformance directory](https://github.com/velella-sh/offing/tree/main/docs/spec/release-gate/conformance) into the same directory and run `node check.mjs` with Node.js 22 or newer. The standalone runner checks the date, verdict, and exception rules without Offing. The fixtures and runner are also included in the npm package.
