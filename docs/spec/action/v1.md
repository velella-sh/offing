# Offing GitHub Action v1 contract

This specification defines version 1 of the Action interface. The contract version is independent of the package version and the Git ref consumers use. Choose a published Action release that declares support for this contract. Compatible revisions may add optional inputs or outputs.

## Inputs

Every input is optional. The default scans the checkout offline, annotates findings, writes a local JSON report, and fails at high severity. Pass inputs in `with` only to enable the behavior you need.

| Input | Default | Meaning |
| --- | --- | --- |
| `path` | `.` | Repository root or subdirectory to scan; `.` is the checked-out repository. |
| `paths` | empty | Multi-line list of directories or globs (for example `packages/*`) relative to `path`. Each match is scanned in one run; findings go into one report and SARIF, with a job-summary section per package. Empty scans only `path`. |
| `sbom` | empty | Local CycloneDX, SPDX or Syft JSON file within `path`. Use with `mode: scan` and an empty `paths`. The scan, severity gate and report outputs use this SBOM. |
| `baseline` | empty | Baseline path relative to `path` (or to each matched package when `paths` is set). Empty reports every finding; a configured path that is missing fails the Action, except during same-repository onboarding. |
| `release-gate-days` | empty | Evaluate one root or SBOM in scan mode using this inclusive UTC day window. Blocks on unexcepted dated lifecycle deadlines and warns about missing evidence. Writes the decision to the Job Summary. See the [release gate contract](../release-gate/v1.md). |
| `min-support-days` | empty | Warn (medium severity) on lines whose support ends within this many days; off when empty. |
| `baseline-warn-days` | `14` | Warn when a baseline suppression expires within this many days (0 to 365). |
| `on-expired` | `resurface` | What a baseline suppression does after its `expires` day: `resurface` (its finding is reported again) or `fail` (also fail the job). |
| `policy` | empty | Local fleet policy under `path` or a remote policy already pinned in the runner cache. Policy loading stays offline. |
| `fail-on-severity` | `high` | Lowest failing level: `none`, `info`, `low`, `medium`, `high`, or `critical`. |
| `mode` | `scan` | `scan` scans the checked-out tree. `diff` compares the pull request base and head SHAs from the event payload and fails only on findings the pull request introduces. See the [diff mode guide](../../GITHUB_ACTION.md#pull-request-diff-mode). |
| `annotations` | empty | Which findings become workflow annotations: `changed` annotates only findings on lines the pull request added or changed (the default in diff mode), `all` annotates every finding (the default in scan mode), `none` emits no annotations. Findings left out stay counted in the summary and the JSON report. |
| `report-name` | `offing-report` | Deprecated. Override the default artifact name when `upload-report` is `true`. |
| `upload-report` | `false` | Upload the JSON report as an Actions artifact. The report is always written locally after a completed scan. |
| `sarif` | `false` | Write SARIF locally with no code scanning permission. |
| `upload-sarif` | `false` | Set to `true` to upload the findings to GitHub code scanning as SARIF. Needs `security-events: write`. |
| `upload-badge` | `false` | Generate a Shields.io endpoint JSON and a branded SVG badge, and upload both as the `offing-badge` artifact (14 days). |
| `forecast` | `false` | Publish the lifecycle forecast in the job summary, the pull request comment, and a calendar artifact. See [lifecycle forecast](../../forecast-action.md). |
| `forecast-months` | `6` | Forecast horizon in whole months, from 1 to 36. |
| `pr-comment` | `false` | Set to `true` for the [countdown and findings summary](../../PR_COMMENT.md). Posting and updating a comment needs `pull-requests: write`. Fork PRs get the summary on the workflow run. |
| `agent-authors` | `Copilot, google-labs-jules[bot], devin-ai-integration[bot], chatgpt-codex-connector[bot], claude[bot]` | Comma-separated logins treated as coding agents. In diff mode, when the pull request author matches, the comment adds the **Stale choices this agent introduced** section. Set to `none` to turn it off. Matching ignores case and a leading `@`. |
| `suggest-fixes` | `false` | In diff mode, post one review whose `suggestion` blocks apply the deterministic fixes for findings on lines the pull request changed. Re-runs update the same review. Needs `pull-requests: write`; pull requests from forks are skipped. |
| `commands` | `false` | Set to `true` to answer `/offing explain` and `/offing ignore` comments when the workflow runs on `issue_comment`. Replies only to owners, members, and collaborators. Needs `pull-requests: write`. |
| `fix-pr` | `false` | Maintain one deterministic fix pull request on `offing/fixes` from the default branch. Runs on schedule or manual dispatch in non-fork repositories. Requires `contents: write` and `pull-requests: write`. See [the fix PR guide](https://velella.sh/offing/FIX_PR/). |
| `fix-pr-labels` | empty | Comma-separated existing labels to add to a fix pull request on creation or update. Omit to leave labels alone. |
| `tracking-issue` | `false` | Set to `true` in a scheduled workflow to keep one issue listing findings by end-of-life date. Re-runs update the same issue; it closes when nothing is left and reopens when findings return. Needs `issues: write`. |
| `github-token` | job token | Token used for PR comments (including the forecast), command replies, fix suggestions, fix pull requests, and the tracking issue. |
| `attribution` | `true` | Deprecated. Adds one line to the job summary saying the scan was done by Offing, with a link. Set to `false` to leave it out. |

## Outputs

| Output | Availability after a completed scan | Meaning |
| --- | --- | --- |
| `report-path` | Always | Absolute runner path to the generated JSON report, whether or not `upload-report` is enabled. |
| `finding-count` | Always | Number of findings remaining after baseline comparison, encoded as a decimal string. |
| `has-new-findings` | Always | `true` when at least one finding remains after baseline comparison, `false` otherwise. In diff mode it covers the findings the pull request introduces. |
| `highest-severity` | Always | The highest remaining severity (`info`, `low`, `medium`, `high`, or `critical`), or empty when there are no findings. |
| `next-eol-date` | Always | The earliest end-of-life date among the remaining findings (`YYYY-MM-DD`), or empty when no finding carries a deadline. |
| `next-eol-days` | Always | Signed decimal number of UTC calendar days from the report's `scannedAt` day to `next-eol-date`. Negative means overdue, zero means today, and empty means no dated finding. |
| `findings-json` | Always | The remaining findings as one compact JSON array. Each entry has `id`, `ruleId`, `severity`, `title`, `path`, and `line` and `deadline` when known. |
| `badge-path` | When `upload-badge` is `true` | Absolute runner path to `offing-badge.json`; otherwise empty. |
| `badge-svg-path` | When `upload-badge` is `true` | Absolute runner path to `offing-badge.svg`, next to the JSON; otherwise empty. |
| `sarif-path` | When `sarif` or `upload-sarif` is `true` | Absolute runner path to the generated SARIF file; otherwise empty. |
| `fix-pr-url` | When the run changed a fix PR | URL of the PR opened, updated or closed. Otherwise empty. |
| `fix-pr-number` | When the run changed a fix PR | Decimal number of the same PR. Otherwise empty. |

## Exit status

- Exit 0 means the scan completed without failing the configured gate, or the Action handled an enabled comment command instead of scanning.
- Exit 1 means the scan was blocked by the release gate, severity gate, or expired-suppression policy, or an input or scan error prevented normal completion. A completed scan still sets its outputs and writes its requested files when a gate fails. A command-only run and an error before the scan completes can leave scan outputs unset.
- An enabled artifact upload or code scanning step can also fail the Action after the scan. Use `if: always()` on a downstream step to inspect outputs after a failure.

## Permissions and files

Grant `contents: read` to the job that checks out the consumer repository. A scan with default inputs performs no uploads or repository writes. The scan uses the data bundled with the Action and requires no registry access.

| Opt-in | Additional GitHub token permission | Result |
| --- | --- | --- |
| `upload-report` | None | Upload `offing-report.json` as `offing-report` by default, retained for 14 days. The report can include matched source excerpts. |
| `sarif` | None | Write a local SARIF 2.1.0 file describing the findings that remain after baseline filtering. |
| `upload-sarif` | `security-events: write` | Generate the same SARIF and send it to code scanning under category `offing`. GitHub code scanning must be available. |
| `upload-badge` | None | Upload the JSON endpoint and SVG as `offing-badge`, retained for 14 days. |
| `forecast` | None for the summary and calendar | Write the forecast to the summary and upload a calendar when available as `offing-forecast`, retained for 14 days. A PR comment uses the permission below. |
| `pr-comment`, `suggest-fixes`, `commands` | `pull-requests: write` | Post or update a comment, post a fix suggestion review, or reply to an authorized comment, respectively. |
| `tracking-issue` | `issues: write` | Maintain a lifecycle issue on schedule or manual dispatch. |
| `fix-pr` | `contents: write` and `pull-requests: write` | Maintain a fix branch and PR, subject to repository settings. Successful publication uploads the canonical verify JSON, patch and refusal list as a run artifact for 14 days. |

For a pull request from a fork, use read-only permissions. With `pr-comment: true`, the job summary shows the same report as the same-repository PR comment. Disable other write features as needed. A same-repository `offing/onboarding` PR with a configured baseline that is missing can propose the baseline in a PR comment when the token allows it, even when `pr-comment` is false. If posting fails, the Action warns.

File outputs are absolute paths on the same runner. Files are written to the runner's temporary directory when configured. Transfer files to another job using an explicit artifact upload and download.

## Conformance

Use the [consumer workflow and standalone runner](conformance/README.md) to check a built Action from an isolated checkout. Look for `acc-action-v1` in the pull request checks and release jobs.
