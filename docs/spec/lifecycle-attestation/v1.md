# Lifecycle attestation v1

The predicate type is `https://velella.sh/offing/attestation/v1/` and the envelope is an [in-toto Statement v1](https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md). A release may carry this statement alongside SLSA provenance. This predicate describes lifecycle evidence available when the producer observed the artifact.

The [JSON Schema](https://velella.sh/offing/schemas/lifecycle-attestation.v1.schema.json) describes the enclosing statement. Its `$defs/predicate` definition describes the object to pass to a signer.

## Subject

`subject` lists one or more artifacts in the in-toto resource descriptor format. Every subject carries a lowercase SHA-256 digest in `digest.sha256`. Producers compute it over the exact artifact bytes or supply an existing SHA-256 digest for a subject such as an OCI manifest. `name` is optional and informational. Verifiers hash the exact bytes and match the digest to an entry in `subject`.

## Predicate

| Field | Meaning |
| --- | --- |
| `builtOn` | Producer's UTC calendar day at build-time observation, written `YYYY-MM-DD` |
| `offingVersion` | Version of the producer that recorded the observations |
| `ebb.version` | Version of the Ebb data active during the observation |
| `ebb.digest` | Ebb content address, `sha256:<64 lowercase hex digits>` |
| `ebb.signature` | Optional verified Ebb data signer `issuer` and `identity`, and the `bundleUrl` of the matching Ebb release for standard Ebb signers |
| `input` | `scan` for repository findings or `sbom` for observations from a local bill of materials |
| `components` | Observations with lifecycle data and their status and rules at build |
| `noData` | Observations for which the producer could not report an evidence-backed status |

An observation carries a versionless, canonical `purl` or an input `name` if it has no usable PURL. `version`, when present, is the exact version considered, with a PURL-embedded version taking precedence over an SBOM's version field. `location` carries a repository-relative path or an SBOM JSON Pointer. The version and location distinguish multiple observations of the same PURL.

`affected` means at least one recorded rule applied. `not-affected` means the dataset had rules for the PURL and none applied at the observed version, so `rules` is empty. `version-dependent` means the producer lacked the version needed to select among the recorded candidate rules. Consumers retain each `noData` entry as an unknown. An empty observations array is permitted. Repository scans represent only findings and the unclassified references the detectors surfaced. To enumerate an artifact's components, supply a CycloneDX, SPDX 2.3 or Syft JSON SBOM, including SBOMs of container images. The caller is responsible for supplying the SBOM of the same artifact whose bytes or digest are attested.

For signed cached or pinned Ebb data, the content address is the bundle manifest's verified `contentDigest`. For Ebb's bundled data, compute the same address over Ebb's required registry and SHA-map paths: canonicalize each file with Ebb's canonical JSON algorithm, hash its UTF-8 bytes, then hash the concatenation of `<path> <sha256>\n` lines sorted lexically by path. See [Ebb data bundles](https://github.com/velella-sh/ebb/blob/main/docs/DATA.md).

## Lifecycle fields

Each rule in a component has a distinct ID. The rule fields preserve the corresponding [Ebb registry v2](https://github.com/velella-sh/ebb/blob/v0.2.0/schemas/registry.v2.schema.json) and [SBOM lifecycle property](https://velella.sh/offing/spec/lifecycle-properties/v1/) meanings:

| Predicate field | Ebb or input field | Lifecycle properties v1 |
| --- | --- | --- |
| Component `purl`, `version` | Registry rule `purl`, resolved version checked against `vers` | Component PURL and version |
| Component `status`; `noData` | Result of observing a rule or checking the component against the available data | Lifecycle properties are emitted for applicable milestones |
| `rules[].ruleId` | `id` | `offing:lifecycle:ruleId` |
| `rules[].event`, `date` | `event`, optional `deadline` | `end-of-support` maps to `cdx:lifecycle:milestone:endOfSupport`. `end-of-life` and `scheduled-end-of-life` map to `cdx:lifecycle:milestone:endOfLife`. Other rule events retain their Ebb meanings. |
| `rules[].sources` | `sources[].url` | `offing:lifecycle:source` and evidence references |
| `rules[].replacement` | `replacement` | `offing:lifecycle:replacement` |
| `rules[].daysLeftAtBuild` | Derived from the rule deadline and the build day | Relative day count for the same absolute deadline |
| `builtOn`, `offingVersion`, `ebb`, `input`, observation `location` | Snapshot context, producer and Ebb provenance, input origin | Statement metadata |

## Date evaluation

Dates are real UTC calendar dates in years 0100 through 9999. If a rule provides `date`, it must also provide `daysLeftAtBuild`, and the two fields must agree with `builtOn`. Interpret each midnight UTC as an integer day and subtract the build day from the rule day. In particular, zero is the rule day and negative numbers count elapsed days. When the rule has no date, both fields are absent. For example, from 2024-02-28 to 2024-02-29 the result is 1, and from 2024-03-01 to the same rule date it is −1.

First authenticate a signed bundle against the expected workflow identity and subject bytes. Validate the statement and check the recorded day count. To re-evaluate it as of today, subtract today's UTC day from the rule day for each dated observation. The projection consumes the signed evidence as recorded at build. A new Ebb snapshot requires a new observation and statement.

## Conformance

Download the [standalone checker](https://velella.sh/offing/spec/lifecycle-attestation/conformance/check.mjs) and [fixtures](https://velella.sh/offing/spec/lifecycle-attestation/conformance/fixtures.json) into a `conformance` directory. Put the [reference verifier](https://velella.sh/offing/spec/lifecycle-attestation/example/verify.mjs) into a sibling `example` directory. Use Node.js 22 or newer.

```sh
node conformance/check.mjs statement.json
node conformance/check.mjs --suite node example/verify.mjs
node example/verify.mjs statement.json artifact.bin 2026-05-15
```

The suite records the expected verdict for every case, including an empty observation set, the leap-day projection, unsupported statement types, malformed digests, invalid dates and inconsistent day counts. The reference verifier matches artifact bytes and projects the valid statement without installing Offing. See [Sign and verify a lifecycle attestation](https://velella.sh/offing/ATTESTATION/) for the full signature verification flow.
