# Runtime upgrade simulation v1

Use `offing forecast <path> --target <runtime@version> --json` or the MCP tool `simulate_upgrade`. A request can include up to eight targets in order. A version names a numeric release line such as `nodejs@22` or `python@3.13`. Targets are independent scenarios. `--as-of` or MCP `as_of` sets the UTC reference date, which defaults to today. The horizon defaults to 12 months and accepts 1 through 36 months.

The [JSON Schema](https://velella.sh/offing/schemas/whatif.v1.schema.json) governs both report kinds. Each report carries `schemaVersion`, `kind`, `today`, and `reports`.

## Repository reports

Each element names its `target`, verdict, analyzer IDs, compatibility `issues`, `blockers` grouped by direct dependency, target `support`, runtime `pins`, and projected `forecast`. File locations are relative to the analyzed root. Lines are one-based. Large MCP answers may include a `more` pointer to the complete CLI report.

- `blocked` means an analyzer found a blocker or the target line has ended.
- `unknown` means the target line has no known lifecycle date, compatibility evidence was absent, or an analyzer reported an unknown. A lifecycle-only result cannot establish compatibility.
- `ready` means the target has a known lifecycle date and an applicable static compatibility analyzer found no blocker or unknown. Build, test, infrastructure, and dependency resolution outcomes remain untested.

Support records the target's known end date and its rule and source. `no-data` indicates the bundled data does not establish a date or ended status. When the migration path finds a later supported line with a longer dated window, `next` records that line and date.

Each differing pin reports its file, literal, normalized release and field. A container pin can carry the contributing image chain. `substituted` names a hypothetical replacement at the location. `unresolved` covers ambiguous declarations and image variants, digests, or expressions. No substitution runs or changes a file.

Forecast arrays report dated obligations by rule and location through `until`, including overdue obligations. `removed` requires proof that the projected literal falls outside the old rule's range. `retained` includes unrelated and unresolved obligations. `added` lists known events on the projected line. Package dependencies and unclassified release dates are not invented.

With `--effort` or MCP `effort: true`, each pin or issue has an evidence-backed effort result. `automatic` identifies a deterministic patch for the requested release. `assisted` identifies a finding-specific migration packet an agent can use. `manual` records why a deterministic patch or a packet does not establish the change. These labels describe proposed work. The report has no measured Autopilot success rate.

## Saved fleet reports

Record pinned static evidence using `offing fleet <organization> --json --what-if-target <runtime@version>` before running `offing forecast --fleet <fleet.json> --target <runtime@version> --json`. Capture is opt-in and can contain private paths and compatibility reasons. The consumer reads the saved JSON offline.

Each target lists the `ready`, `blocked`, and `unknown` repositories. Entries preserve the host, repository name, commit and reason. The reader only accepts captured evidence for the exact target and reference date on scanned or cached rows with a commit. Aggregate-only, skipped, failed, other-target and stale records are unknown. With no explicit date, a recording with one evidence date uses it. Mixed dates require the reader to select one to use evidence. The file is a recording, with no signature or authenticity guarantee.
